# Tool Page Rubric

> **Live-site mismatch — read first.** The body of this rubric below describes the **non-live tailwind site** (`sites/astro-tailwind-terminal1`): single-page tool entries at `src/content/tools/{name}.md`, frontmatter validated by the `tools` zod schema in `src/content.config.ts`, and sidebar coupling via `src/data/tools.ts`. **That site is no longer live.** The live site (per `SITE_DIR` in `.github/workflows/deploy.yml`, swap `fbb046f`, 2026-05-31) is **Starlight** (`sites/astro-starlight-terminal1`): tools are **multi-page** (`src/content/docs/tools/<tool>/{overview,install,commands,workflows}.{md,mdx}`), the sidebar is **hardcoded in `astro.config.mjs`** (no `src/data/`). Fully reconciling this rubric's body to Starlight is a separate concern (the rubric predates the swap); this file currently carries the Starlight-aware additions below (the [Command reference exception](#generated-command-reference-exception) and onward, including the [site chrome overrides](#site-chrome-overrides-header-logo-footer-head-change-i2b0)).

## Overview

Every tool documented at `src/content/tools/{name}.md` follows the same shape. The rubric is short on purpose — these pages are "directory entries" pointing to each tool's full README on GitHub, not full docs.

This pattern is observable across all seven tool pages (`idea.md`, `hop.md`, `fab-kit.md`, `wt.md`, `run-kit.md`, `tu.md`, `shll.md`) and is the expected shape for any new tool added to the toolkit.

## Requirements

Every tool page MUST contain the following sections, in order:

1. **Frontmatter** — `title` (the tool name) and `description` (one sentence, ≤140 chars, the elevator pitch). MUST satisfy the `tools` collection schema in `src/content.config.ts` (zod: `{ title: string, description: string }`).
2. **Opening paragraph** — One short paragraph (1-2 sentences) describing what the tool is. SHALL NOT exceed two sentences.
3. **`## Install`** — A `bash` code block with the `brew install sahil87/tap/{tool}` line and any required shell-init eval (e.g., `eval "$(tool shell-init zsh)"`).
4. **`## At a glance`** — A `bash` code block with 4-6 representative commands and inline `# comment` annotations. Followed by a bulleted list of distinguishing properties (3-6 bullets).
5. **`## Full docs`** — One sentence pointing to the GitHub README, followed by `**→ [github.com/sahil87/{tool}](https://github.com/sahil87/{tool})**` as the link.

Tool pages SHALL NOT contain **hand-written**:

- Long-form command reference (every flag, every subcommand) — **except** the *generated* Command reference described in [the exception below](#generated-command-reference-exception). This rule still stands for hand-written content; the exception is narrowly for binary-generated reference.
- Architecture diagrams, Screenshots, or deep long-form prose — **except** the *mechanically-synced* README slice described in [the pulled-README-slice exception below](#pulled-readme-slice-exception-change-w32m). The old blanket bans on diagrams/screenshots/depth applied to **hand-copied** content; they no longer apply to content pulled-and-synced from the tool's canonical repo.
- Changelog or version history (hand-written; a tool's own README `## Changelog`, if present, may travel into the pulled slice — it is not denylisted by the extraction contract).

> **Stance revised (change `w32m`, constitution v2.1.0; refined `4s3e`, v2.1.1).** The earlier "site is a thin directory / link out for depth / no screenshots / no diagrams" stance is **superseded** by the constitution's **Tool-Page Depth** constraint ([`constitution.md`](../../../fab/project/constitution.md) v2.1.1). Tool pages MAY now host deep per-tool prose, referenced screenshots, and rendered diagrams — **provided** the content is mechanically synced from the canonical tool repo (README slice today; `docs/site/` reserved/future), never hand-copied. The anti-drift *value* behind the old stance is preserved and made explicit: single-source + mechanical sync (the producer repo stays canonical), not thinness.
>
> **The overview is thin again — but for a DIFFERENT reason than the original stance (change `4s3e`; lead+linking thickened by change `bees`).** The original "short pages" stance kept the overview thin because *depth lived on GitHub* (link out). Under `4s3e` the **overview is once more a thin directory entry**, but depth is now **ON the site** — on the dedicated [`readme` page](#pulled-readme-slice-exception-change-w32m) (sourced from the canonical README), not on GitHub. Do not mistake the thin overview for a return to "link out for depth": depth moved to a sibling synced page, not off-site. Its current shape (change `bees`) is: `<GithubButton>` + a **3–4-sentence job-framed lead** + a **`## How it fits` cross-tool linking subsection** + the `## Where to next` nav links to readme/commands/[install]/[workflows] — see [the overview body shape below](#overview-body-shape-site-authored-framing--cross-tool-linking-change-bees). Still thin (framing, not depth), just no longer a single terse sentence. The `vn39` cross-check is now **report-only** for the pulled slice (it surfaces divergence as a CI warning, it does not block the canonical README) — a hard rule only for hand-written prose. Both generated/synced exceptions below realize this (each as a dedicated sibling page).

## Overview body shape: site-authored framing + cross-tool linking (change `bees`)

The site-authored `overview.mdx` body is **still thin** (framing, not depth — depth lives on the synced [`readme` page](#pulled-readme-slice-exception-change-w32m)), but its shape was sharpened by change `bees` (the editorial/content SEO pass — full story in [seo-social-meta → Editorial layer](/conventions/seo-social-meta.md#editorial--content-seo-layer--change-bees)). The current shape of every `tools/<tool>/overview.mdx` body:

1. **`<GithubButton tool="<slug>" />`** — the persistent jump-to-repo affordance (see [Per-tool GitHub affordance](#per-tool-github-affordance-live-starlight-site)).
2. **A 3–4-sentence job-framed lead** — "what is `<tool>` / why use it / who it's for", surfacing ranking keywords in the first indexable paragraph. This **replaced the prior 1–2-sentence terse framing** the rubric used to describe (e.g. idea's old single sentence became a 4-sentence lead). The bare-slug Starlight `title:` (the H1) is **unchanged** — it cascades to the sidebar label and the settled [`kb1r` `shll | shll` title discipline](/conventions/seo-social-meta.md#homepage-head-overrides-starlightpage-frontmatterhead); the keyword framing lives in the body lead, not the title.
3. **A `## How it fits` subsection** — a one-line-context paragraph linking the **adjacent tools in the `idea→fab-kit→wt→run-kit` workflow chain** (plus `tu`/`hop` cross-cutting, `shll` bootstrap). `bees` authored these as the relative `../../<tool>/overview/` idiom; **change `3ke3` switched them to site-absolute `/<tool>/`** (and the sibling readme/commands links to `/<tool>/readme/` and `/<tool>/commands/`) — under the flat root slug the relative form would resolve wrong (`../readme/` from `/idea/` → `/readme/`), so site-absolute is the simplest correct form. This wired the previously **disconnected 7 overviews into a connected graph** — before `bees`, zero overview linked to any other tool's page. Full per-page link map + rationale: [seo-social-meta → Cross-tool internal linking](/conventions/seo-social-meta.md#cross-tool-internal-linking--the-ideafab-kitwtrun-kit-graph-the-highest-value-bees-item).
4. **`## Where to next`** — the nav links to readme / commands / (where present) install / workflows.

**The `vn39` HARD rule is now load-bearing on this framing prose (change `bees`).** The site-authored framing surfaces are not all "trivially satisfied by naming no commands or flags" — the [landing page's blurb list](#the-landing-pages-hand-authored-copy-surfaces) keeps *its* framing command-free, but the overviews do not: the `bees` job-framed leads actively **name validated CLI tokens** — `run-kit riff`, `run-kit serve` (run-kit — `rk` before the `co63` v3.0.0-rename sweep), `shll install`, `shll update` (shll), `git worktree` (wt), and shell builtins like `cat`/`grep`/`git diff`. So the [`vn39` hard rule for hand-written prose](#pulled-readme-slice-exception-change-w32m) is now **actively binding** on the overview bodies (every named command/flag MUST resolve in the relevant `help/<tool>.json`), not vacuously satisfied. The `bees` apply ran the cross-check: `validate-help.mjs` passed 7/7 and every CLI token resolved.

> **Slash-command skills (`/fab-new`, `/fab-fff`, …) are EXEMPT from `vn39` (change `bees`, confirming `jf3q`).** `help/<tool>.json` carries only the CLI **binary's** subcommands/flags; the `/fab-*` and `/git-pr-review`-style tokens are **Claude Code skills**, absent from every help JSON **by design**. They are a recognized, accurate token category outside the help-JSON cross-check — the `idea` overview already ships "feeds `/fab-new`", and the [`jf3q` audit](#rk-vs-run-kit--the-cli-identity-vs-reposection-naming-rule-change-jf3q) records `fab change new` (CLI) vs. the `/fab-new` skill as ground truth. **File paths** (`fab/backlog.md`) and **shell builtins** (`cd`, `cat`, `grep`) are likewise exempt — they are not `help/<tool>.json` tokens. Do not flag any of these as a `vn39` violation.

This is the overview = **site-authored directory entry** role reinforced — the editorial counterpart of the tool's synced `readme` page (the [canonical own words](#pulled-readme-slice-exception-change-w32m)). The two authors stay cleanly separated: framing here, depth there.

## Overview body shape: `## Install` section + `## Screenshots` (change `moju`)

Change `moju` added two more elements to the overview body shape above, extending the section order to: `<GithubButton>` → job-framed lead → **`## Install`** → (**`## Screenshots`** where present) → `## How it fits` → `## Where to next`.

### The `## Install` one-liner (all 7 overviews)

Every `tools/<tool>/overview.mdx` now carries an `## Install` section between the job-framed lead and `## How it fits`, rendering a shared build-time component:

```mdx
import InstallOneLiner from '../../../../components/InstallOneLiner.astro';

## Install

<InstallOneLiner tool="<slug>" />
```

- **`src/components/InstallOneLiner.astro`** takes a `tool` slug prop, **validates it against the shared roster** (`isToolSlug` from `src/lib/tool-slugs.ts` — the same gate the root-namespace dispatchers use), and **fails the build** on a missing prop (required) or an unknown slug (names the offender), mirroring `GithubButton`/`CommandReference`'s top-level guards. It renders an **Expressive Code terminal block** — Starlight's re-exported `<Code>` component, the same engine and **one-click copy button** as every fenced code block on the site — carrying `curl -fsSL https://shll.ai/install | sh -s -- <tool>` plus one short site-authored note linking to `/toolkit/install/`. (The one-liner URL text still says `shll.ai/install` — the install-script identity is owned by a separate rebrand step.) Build-time rendered; the only client JS is EC's own copy-button script, already shipped by every page with a fenced block — no new dependency (the import is a Starlight re-export, Constitution VI).
- **The component is the SINGLE SOURCE of the per-tool one-liner** — it deliberately does NOT add seven hand-copied install blocks (the repo's `GithubButton`/`VersionTable`/`ToolsIndex` single-source precedent). `toolkit/install.md` is the canonical hand-written carrier of the whole-toolkit quick-start. The [landing page](#the-landing-pages-hand-authored-copy-surfaces) is **not** a consumer — it renders the product-first install lines from its own data module. This component is a **NON-drift surface** (like [`ToolsIndex`'s build-time descriptions](#tools-index-page--the-tools-directory-landing-change-pgox)), not a hand-copy.
- **Three render classes: whole-toolkit, subset, and the follow-on carve-out.** The component resolves each `tool` slug into one of three renders. Two constants sit side by side in the frontmatter: `isShll` (the `tool === 'shll'` carve-out) and a `FULL_TOOLKIT` map keyed by slug (`fab-kit`, `hexokit` — the product's roster slug), each map value a per-tool sibling-dependency reason clause.
  - **Whole-toolkit one-liner (`shll` + `fab-kit` + `hexokit`).** `shll` and the `FULL_TOOLKIT` tools render the whole-toolkit form `curl -fsSL https://shll.ai/install | sh` (no `sh -s -- <slug>`). It is a **single shared base string** `WHOLE_TOOLKIT_ONE_LINER` that both the whole-toolkit branch and the subset branch reuse (the subset appends `-s -- ${tool}`), so the whole-toolkit literal is single-sourced and cannot drift.
  - **Subset one-liner (`idea`, `hop`, `wt`, `tu`).** The remaining four tools each render `curl -fsSL https://shll.ai/install | sh -s -- <own-slug>`, scoped to installing `shll` + that one tool.
  - **`shll`'s reason vs. the full-toolkit tools' reason.** `shll` is the bootstrap meta-CLI, **not a valid `shll install` target** — the installer script execs `shll install "$@"`, and `shll install shll` hard-errors (`shll` is not one of the six installable tools; see `help/shll.json` and `toolkit/install`). Do not "normalize" `shll` back to the `sh -s --` form — it would emit a hard-erroring command. `fab-kit` and `hexokit` render the whole-toolkit form for a different, **tool-intrinsic** reason: each **relies on its sibling tools** (fab-kit on `wt` + `idea`; the product on `wt` for the riff worktree flow), so `sh -s -- <tool>` — while still functional — yields a degraded setup, and each tool's **canonical README** (the constitution's Tool-Page-Depth source of truth) documents the whole-toolkit one-liner as the supported install path. That README stance is the trigger; the sibling dependency is why. Because it is a property of the *tool*, not of the page, the branch lives inside the component next to the `shll` carve-out — **not** as a page-authored prop (rejected: it would scatter a tool-intrinsic fact across pages and reopen the hand-authored drift surface the single-source design closed).
  - **Follow-on block stays `shll`-only.** The `shll shell-setup` / `shll agent-setup` / `exec $SHELL` follow-on `<Code>` block renders **only** for `tool === 'shll'`. The `FULL_TOOLKIT` tools render the whole-toolkit one-liner plus a note (sibling-dependency reason + "so the full-toolkit install is the supported path", keeping the `/toolkit/install/` link) but **no** follow-on block — the overview install section stays light and the note's link carries the visitor to the full guide.
- **Why an `.astro` component, not inline MDX prose.** The one-liner contains both `--` and a bare URL; MDX's remark/smartypants pass mangles those (em-dash + auto-link) even inside `<pre>` (the documented `index.mdx` remark-hazard). The command is built as a plain JS string and handed to `<Code>` as a prop, so the literal command survives verbatim — in the render AND in what the copy button copies. (The original select-none `$`-prompt selection-copy idiom was replaced by the EC copy button in the same follow-up PR.)
- **`vn39`-clean.** The line names only `curl`/`sh` (exempt shell tokens) and no tool-binary subcommands/flags, so it introduces no `help/<tool>.json` cross-check friction — even though it is now hand-placed on every overview alongside the `bees` leads.
- **Link styling rides the ONE shared terminal-link selector group.** The note's `<a>` styling is NOT scoped in the component — `.install-one-liner-note a` was joined to `terminal.css`'s single terminal-link selector group (`.shell-session a, .home-prose a, .tools-listing a, .install-one-liner-note a` — base + hover/focus), the same one-source, no-per-class-copies convention `ld0j` established for the homepage/tools-listing links. The component's scoped `<style>` carries only layout/typography (no `a` selectors).

### The `## Screenshots` convention — site-owned curated assets (constitution v2.1.3)

`moju` also formalized the `## Screenshots` section as a **third permitted content class** for overviews, blessed by the constitution's [Tool-Page Depth](../../../fab/project/constitution.md) PATCH **v2.1.3**. This joins the two mechanically-synced exceptions already recorded in this rubric (the [generated `commands` page](#generated-command-reference-exception) and the [pulled `readme` slice](#pulled-readme-slice-exception-change-w32m)) — a **third** permitted content class alongside those two, and the **one hand-placed class exempt from the mechanical-sync requirement**:

- **What it is.** Committed static image assets under the live site (`public/screenshots/<tool>-*.webp`), hand-captured and hand-placed on the overview's `## Screenshots` section (ordered **after `## Install`, before `## How it fits`**).
- **Why the exemption is narrow and justified.** A screenshot is a curated visual capture **versioned in-repo**, not command/flag prose — so the command-drift the mechanical-sync rule guards against does not apply; its only staleness risk is *visual* (a UI that has changed appearance), acceptable for marketing framing and self-evident on inspection. This is the distinction from hand-copied prose/reference (still forbidden).
- **Constraints.** They MUST carry meaningful alt text (the existing Accessibility constraint), SHOULD be `.webp`, and MUST remain **distinct from synced README imagery** — README images keep flowing to the tool's `readme` page mechanically via the [pulled slice](#pulled-readme-slice-exception-change-w32m); do NOT hoist a synced README image onto an overview (that would create a second, hand-placed render of upstream-controlled imagery — the [non-goal `moju` honored for hop/fab-kit](#pulled-readme-slice-exception-change-w32m)).
- **Retroactive coverage.** v2.1.3 **retroactively legitimizes the two run-kit screenshots added by PR #82** (`public/screenshots/run-kit-{agent-session,console}.webp`), which were hand-placed before any rule blessed them.
- **Scope of `moju` itself.** Only run-kit had assets; `moju` **normalized run-kit's existing `## Screenshots` to sit after `## Install`** (no new captures) and added no `## Screenshots` sections to the six tools without assets. Future per-tool screenshots follow as assets are captured, under this blessed class.

## Generated Command reference (exception)

The one permitted exception to "SHALL NOT contain long-form command reference" is a **generated** CLI command reference, sourced from `help/<slug>.json` (see [help-collection](/conventions/help-collection.md)). On the **live Starlight site** it renders as each tool's dedicated **`commands` page** (`sites/astro-starlight-terminal1/src/content/docs/tools/<tool>/commands.{md,mdx}`), filling Starlight's existing "commands … coming soon" slot.

This is permitted precisely because it is **generated, not hand-written** — single-sourced from the binary's own `-h` output, so it cannot drift from the tool the way a hand-copied reference would. The anti-drift intent of the "SHALL NOT" rule is preserved: hand-maintained long-form reference is still forbidden; only binary-generated, single-sourced reference is allowed.

**Placement decision (now realized, change `js1s`).** The reference renders as a **dedicated `commands` page per tool** on the live Starlight site (multi-page docs model), chosen over an expandable `<details>` block on the `overview` page — the per-page model is the idiomatic Starlight shape and fills the existing empty `commands` slot.

The realized form: each tool has `src/content/docs/tools/<tool>/commands.mdx` (frontmatter `title: Commands` + a `description`) that imports `src/components/CommandReference.astro` and renders `<CommandReference tool="<tool>" />`. The component reads + validates + renders `help/<slug>.json` at build time (see [help-collection → Rendering Consumer](/conventions/help-collection.md#rendering-consumer-commandreference)). Pages are `.mdx` (not `.md`) precisely so they can `import` the component.

**Generated replaces hand-written.** idea and fab-kit previously carried hand-written `commands.md` prose; both were **removed** and replaced by the generated `commands.mdx` (a `.md` and `.mdx` at the same slug would collide in Starlight). The curated prose is not lost — its canonical home becomes each command's cobra `Long` field, which flows back through the producer into `help/<slug>.json` and onto the site automatically (tracked as idea backlog `e3rk`, out of scope here). Net effect: **no hand-written command-reference prose remains on any tool page**; the only command reference is the binary-generated one.

**Enriched/structured render + cross-tool index (change `qemq`).** The generated reference surface is now two surfaces, both still single-sourced from `help/*.json` (so the anti-drift guarantee holds):

1. The per-tool `commands` page no longer renders a flat raw `-h` blob — `CommandReference.astro` decomposes each node's captured `text` at build time (via `src/lib/parse-help.ts`) into a **structured view**: command path + copy, description, copyable usage, a flags table with type/required/global badges and per-row copy, a per-command flag filter, and a "show raw" `<details>` fallback (raw stays authoritative). Per-command `-h/--help` rows are suppressed, paired with a once-per-page universal-help note.
2. A new **cross-tool command index** at `/reference/command-index` (in a new "Reference" sidebar group) flattens every command path + real flag across all tools into one searchable list.

Both run at build time (Constitution I) and the parse is **display-only** — it never derives the command tree (still sourced from JSON `commands[]`), so it does not violate the help-dump contract §5 nor the anti-drift intent of this exception. Mechanics live in [help-collection → Rendering Consumer](/conventions/help-collection.md#rendering-consumer-commandreference).

## Any site-displayed version number is a synced value

Any per-tool version number rendered on the site MUST be read from `help/<slug>.json` at build time — it SHALL NOT be hand-typed. This extends the mechanical-sync principle beyond the generated `commands` page and the pulled `readme` slice to version strings, which drift on every release when hand-maintained. (The rule was written after an audit found all seven hand-typed homepage versions stale, one of them a *fabricated* `v1.4.2` lifted from a planning-doc placeholder — `jf3q`.) The landing page's hero eyebrow follows it: it reads `version` from `help/hexokit.json` through `normalizeVersion`.

**`VersionTable.astro` is the realized component, currently unmounted.** It renders a terminal `$ shll version` block — one `shell-line` per rostered tool (label column + `shell-dim` version + a `[git]` link, column-aligned under `white-space: pre`). It is committed and no page renders it; the homepage that did is now the [landing page](../../../sites/astro-starlight-terminal1/docs/memory/site/landing-page.md), whose eyebrow reads a single version directly. Its contract, should it be mounted again:

- **Site-authored data comes from the shared roster, NEVER from JSON**: the roster, display order, display labels, route links (`/<mount>/`), and repo URLs resolve from `TOOL_ROSTER` ([tool-roster](/conventions/tool-roster.md)). **Only the `version` string is sourced from JSON.** This keeps site presentation site-authored while versions self-correct — the producer repo does not dictate presentation.
- **Self-correcting**: when a scheduled-puller commit bumps a `version` in `help/*.json`, the next rebuild reflects it with **zero source edit**.
- **Mirrors `CommandIndex.astro`'s read+validate pattern** — `repoRootFromModuleUrl(import.meta.url)` (`src/lib/repo-root.ts`) + `HelpDocSchema.parse` (`src/lib/schemas.ts`; `version` is `HelpDocSchema`-required). It reuses both shared libs, no reimplementation (consistent with the two-consumer posture in [help-collection](/conventions/help-collection.md#rendering-consumer-commandreference)).
- **Build-stopping on missing/invalid JSON** (mirrors `CommandIndex.astro`): a missing or schema-invalid `help/<slug>.json` throws with a descriptive error naming the offending file — a stale/missing-version defect MUST NOT deploy. This is the **opposite** of the landing eyebrow's skip-degrade posture, and deliberately so: a table that claims to list every tool's version is wrong if one is missing, while a single decorative badge is not.
- It is a **build-time read** (Constitution I — no runtime fetch, no new dependency, Constitution VI) and emits plain `shell-*` markup, so dark-mode parity (Constitution V) holds for free.

## `/tools` index page — the tools directory landing (change `pgox`)

The tools **directory landing** is the **`/toolkit/` overview** (`src/content/docs/toolkit/index.mdx`), which renders `<ToolsIndex />` — the family listing lives with the family content. The old `/tools/` page (`tools/index.mdx`) is removed and `/tools` is a static redirect to `/toolkit/` (a redirect key colliding with a real route fails the Astro build, so the page must be gone for the redirect to exist) — see the [Design Decision](#design-decisions). The companion breadcrumb crumb (`Toolkit` → `/toolkit/`) resolves there — see [seo-social-meta → Per-tool branch](/conventions/seo-social-meta.md#per-tool-branch--softwareapplication--breadcrumblist-mount-gated).

- **`src/components/ToolsIndex.astro`** — the build-time listing, **mirroring `VersionTable.astro`'s read+validate+render shape**, iterating the shared **`TOOL_ROSTER`** from [tool-roster.mjs](/conventions/tool-roster.md) (route `/<mount>/`, label from the record, repo via `repoFor`) rendered as a `<ul class="tools-listing">` reusing the **existing** `.tools-listing` / `.tool-desc` `terminal.css` classes (dark-mode parity via `--c-*` tokens for free — Constitution V; zero new styles). It reuses `repoRootFromModuleUrl(import.meta.url)` + `HelpDocSchema.parse` (both shared libs, no reimplementation).

**The tool one-liners are a NON-drift surface — build-time JSON-single-sourced, unlike the documented hand-copy surfaces.** This is the key distinction from the [landing page's hexagon blurb list](#the-landing-pages-hand-authored-copy-surfaces), a hand-copy drift surface: the listing's **only** JSON-sourced value is each tool's `description`, read verbatim from `help/<slug>.json` `root.short` at build time. The roster, display order (product first, then the hexagon order, then shll), display labels, and routes come from the shared roster. This deliberately keeps the page from becoming a hand-copy of tool descriptions — it self-corrects whenever the scheduled puller bumps a `root.short`, with zero source edit.

> **Verbatim `root.short` carries a binary prefix (intentional).** The listing renders `root.short` verbatim, so the product's row reads `run-kit — tmux session manager with web UI` (from `help/hexokit.json`, envelope `tool: "run-kit"`) — differing from the homepage `TerminalPrompt`'s `stripToolPrefix` treatment. Single-sourcing verbatim beats a second strip path; see [seo-social-meta](/conventions/seo-social-meta.md#per-tool-branch--softwareapplication--breadcrumblist-mount-gated).

**Build-stop posture (`VersionTable`'s, NOT the JSON-LD soft-miss).** `ToolsIndex.astro` **stops the build** on a rostered `help/<slug>.json` that is missing or schema-invalid (error wrapped with the file + slug) — because a committed directory page must list every tool; an incomplete roster is a defect that must not deploy (mirrors `VersionTable`/`CommandIndex`). This is the **opposite** of the inert [per-tool JSON-LD branch](/conventions/seo-social-meta.md#per-tool-branch--softwareapplication--breadcrumblist-mount-gated), which soft-omits a missing description and keeps building. The two surfaces split on correctness criticality, exactly as the [`d9qb` star-count fail-soft vs. `VersionTable` build-stop](#per-tool-github-affordance-live-starlight-site) distinction does.

> **MAINTENANCE — what self-updates vs. what needs a code edit.** Split the surface into two halves so a future maintainer knows where the manual seams are:
>

## Per-tool pages are canonical at the root namespace — change `3ke3`

The three per-tool pages — the hand-authored `overview` and the two generated/synced pages (`readme`, `commands`) — are **canonically served at the site root** under the roster's **mount** segment: `/<mount>` (overview), `/<mount>/readme`, `/<mount>/commands`. For the six companions the mount equals the slug (`/wt`, `/idea/`, …); for the product the mount is **`docs`** — the `hexokit` overview lives at `/docs/` (see [tool-roster](/conventions/tool-roster.md)).

- **Mechanism — Starlight `slug:` frontmatter overrides, NOT file moves.** Each `src/content/docs/tools/<slug>/{overview,readme,commands}.mdx` gains a `slug:` override naming the mount (`slug: <mount>`, `slug: <mount>/readme`, `slug: <mount>/commands` — for the product's `tools/hexokit/*` files those are `docs`, `docs/readme`, `docs/commands`). The files stay physically under `src/content/docs/tools/` — Astro's content-layer glob loader maps frontmatter `slug:` directly to the entry `id`, and Starlight derives the route from that `id`. So this is a route mapping with zero file churn.
- **Retired URLs are static redirects.** `astro.config.mjs` `redirects:` carries the reverse entries, all enumerated programmatically from the roster (Astro static builds cannot wildcard): `/tools/<name>` + `/tools/<name>/overview|readme|commands` → `/<mount>/…` (keyed by slug AND `legacyMounts`), one `/tools/<name>/<path>` per committed docs/site page plus `/<legacy>/<path>` per legacy mount (via `docsSiteRedirectEntries` — see [docs-site-tree → redirect enumeration](/conventions/docs-site-tree.md#the-redirect-enumeration)), the bare legacy mounts (`/run-kit`, `/run-kit/readme`, `/run-kit/commands` → `/docs/…`), and the retired family pages (`/tools` → `/toolkit/`, `/getting-started/*` and `/workflows/*` → `/toolkit/…`).
- **The namespace duty moved to a shared roster gate.** A bare `([^/]+)/readme` regex is fragile (false-positives against root-shaped routes), so every dispatcher gates on roster membership via the shared **`src/lib/tool-slugs.ts`** (the typed re-export of `tool-roster.mjs`): `commands-toc.ts` (route id `<mount>/commands`), `readme-toc.ts` (`<mount>/readme`), and `Head.astro` (the per-tool JSON-LD pathname gate) match on `isToolMount(segment)` and resolve the slug via `slugForMount`. The roster is deliberately site-authored (like `VersionTable`'s) — the producer repos do not dictate the route map.

### Root-namespace reservation ("adding an 8th tool") — change `3ke3`

Because tool mounts live at the site root, a future tool's mount MUST avoid colliding with an existing root route. **Reserved root names** a new tool mount must not use: `docs`, `toolkit`, `desktop`, `tools` (a redirect key), `reference`, `install` (the deploy-time script served at `/install`), `llms.txt`, `llms-full.txt`, `screenshots`, `diagrams`, plus any future root route. The 7 current mounts (`docs`, `fab-kit`, `wt`, `idea`, `tu`, `hop`, `shll`) are all clash-free.

- **No build-time slug-collision guard exists** — with the known clash-free mounts the constraint is **recorded, not enforced** — a guard is cheap to add later if an 8th tool appears. This is the lightest touch consistent with the site's other site-authored rosters.
- **Adding an 8th tool** therefore means: pick a slug/mount outside the reserved set above, add one record to `TOOL_ROSTER` in `tool-roster.mjs`, add its three content stubs with `slug:` overrides, and add it to the homepage `index.mdx` `ls tools/` grid (see the [MAINTENANCE note](#tools-index-page--the-tools-directory-landing-change-pgox)). Optionally declare `legacyMounts` if an old URL was ever shared — the redirect enumeration picks it up.

## Right-rail "On this page" ToC (generated, dispatcher-routed — change `u4di`)

Both **generated/synced** sibling pages — the `commands` page and the `readme` page — carry content Starlight's native right-rail "On this page" ToC **cannot see**, so each needs a custom build-time ToC that fills the rail. The native ToC is built from the `.mdx` file's own heading AST at compile time, but these `.mdx` files contain only a single component call (`<CommandReference .../>` / `<ReadmeSlice .../>`); the real navigable structure lives in a runtime string the AST never sees (the commands page renders `<details>/<summary>`, not headings; the readme slice's `##`/`###` headings live inside a `set:html` string). Result: the two **deepest** pages on the site would otherwise have an empty native rail — a usability regression relative to every other page. The fix mirrors per-source: each page builds its rail from the page's own source of truth (`help/<tool>.json` for commands; `content/<tool>/README.md` for readme).

**The README ToC (`readme` page).** The readme page's rail is sourced from the same `content/<tool>/README.md` slice [`ReadmeSlice`](/conventions/readme-extraction.md#the-readmesliceastro-render-component) renders, as a **nested H2 → H3 tree** (matching the site's `tableOfContents: { minHeadingLevel: 2, maxHeadingLevel: 3 }`). The pieces, all in `sites/astro-starlight-terminal1`:

- **`src/lib/readme-toc.ts`** (build-time helper, the README sibling of `commands-toc.ts`) — detects a `<mount>/readme` route id (`README_ROUTE_RE = /^([^/]+)\/readme$/`, gated on the roster's `isToolMount`, the segment resolved to the slug via `slugForMount`, exported `toolFromReadmeRouteId`), reads the slice via the **`help/`-marker `repoRootFromModuleUrl` ascent** (`lib/repo-root.ts`, the same ascent `ReadmeSlice` uses — anchored on the module URL, NOT a fixed depth, NOT `content/` which collides with Starlight's `src/content/`), re-renders it with `createMarkdownProcessor({})`, reads `rendered.metadata.headings`, and folds the H2/H3 entries into a nested `TocHeading` tree (`{ text, slug, depth, children }`; H4+ ignored; an orphan H3 before any H2 attaches at top level rather than crashing). Failure contract mirrors `firstLevelCommands`: ENOENT → `[]` (page falls back to the default ToC), genuine errors re-throw.
- **`src/components/ReadmeToc.astro` + `ReadmeMobileToc.astro`** (NEW, **separate** from the commands components — the intake mandated separate components, not an extension of `CommandsToc`/`CommandsMobileToc`). Desktop emits a `<starlight-readme-toc>` element wrapping a labelled `<nav>` + "On this page" `<h2>` + a nested H2/H3 `<a href="#{slug}">` list; mobile emits a `<readme-mobile-toc>` `<details>` dropdown mirroring `CommandsMobileToc`'s frame. Both render Starlight's `<Default />` on an empty tree. The static nested list is fully usable with JS disabled (Constitution I); progressive-enhancement scroll-spy (`IntersectionObserver`) tracks **both** levels — it highlights the in-view H3 **and** its parent H2 (`aria-current="true"` on both). This is simpler than the `<details>`-based commands scroll-spy (real headings, no expand-on-click), but observes two heading levels rather than the commands page's flat first-level list.
- **Slug single-sourcing (do not "fix" this).** Both the rendered heading `id`s (`ReadmeSlice`) and the ToC `href`s (`readme-toc.ts`) come from the SAME `createMarkdownProcessor({})` render of the SAME slice, so `href === id` holds **by construction** (verified: 0 mismatches across all 7 tools, dedup suffixes included). NO `github-slugger` direct dependency was declared — see [readme-extraction → Slug single-sourcing](/conventions/readme-extraction.md#slug-single-sourcing-rendered-ids--toc-hrefs-via-one-processor-change-u4di) for the full rationale; a future maintainer MUST NOT add `github-slugger` or a second slug path.

**The dispatcher pattern (reusable convention).** Starlight's ToC override slots are **global and singular** — there is exactly one `components.TableOfContents` and one `components.MobileTableOfContents`. Before `u4di` those slots pointed straight at `CommandsToc`/`CommandsMobileToc`. `u4di` introduces a **route dispatcher** so the single slot can fan out by page:

- `src/components/TocDispatcher.astro` + `MobileTocDispatcher.astro` (NEW) are now the registered override slots in `astro.config.mjs`. Each inspects `Astro.locals.starlightRoute.id` and renders `CommandsToc` for `<mount>/commands`, `ReadmeToc` for `<mount>/readme`, else Starlight's `<Default />` (reusing `toolFromRouteId` + `toolFromReadmeRouteId`, both mount-gated through the roster; the two route regexes are mutually exclusive). Commands-page output is preserved **byte-for-byte** — the dispatcher is a transparent pass-through for commands routes.
- **Convention going forward**: the single ToC override slot is now a dispatch point. The **next** ToC variant (a third generated/synced page type) MUST extend the dispatcher with another route branch — NOT re-add a competing override slot (there is only one) and NOT fall-through-chain among the custom components (rejected at intake: implicit, hard-to-trace routing spread across components). Routing stays central and traceable in the two dispatchers.

**Terminal styling.** `starlight-readme-toc` is added to the existing `terminal.css` ToC selector groups (the `# ` heading prefix, `> ` active marker, mono link colors — shared by `starlight-toc`/`starlight-commands-toc`), plus an H3-child indent. **Footer override — render `<Default />`, then APPEND (never discard).** `src/components/Footer.astro` adds a `© Sahil Ahuja 2026` line site-wide. Starlight's single `Footer` override slot REPLACES the built-in footer — which carries the prev/next pagination (and edit-link / last-updated). To add footer chrome **without losing pagination**, the override renders the built-in `<Default />` first, then appends the copyright `<div>`; it MUST NOT discard `<Default />`. Version note: installed `@astrojs/starlight` **0.39.2**'s default `Footer.astro` takes NO props and renders NO `<slot />` (it self-renders the pagination/edit-link/last-updated from virtual modules + `Astro.locals`), so the version-correct override is a **bare `<Default />`** — no `{...Astro.props}`, no child slot. The copyright color comes from a theme-aware `--c-*` token (`var(--c-fg-dim)` + `var(--sl-text-xs)` mono, from `terminal.css`), so dark-mode parity is automatic (Constitution V) — no hardcoded color.

**The footer copyright row also carries the author links (change `d9qb`) and Discord.** The row reads `© Sahil Ahuja 2026 · MIT licensed · LinkedIn · noon.design · Discord` — the LICENSE link points at `https://github.com/sahil87/hexokit-site/blob/main/LICENSE`; LinkedIn (`https://www.linkedin.com/in/ahujasahil/`), noon.design (`https://noon.design`), and Discord (`https://discord.gg/32XHh5mJYn`) share the single `·`-separated line, reusing the `.site-copyright a` styles (inherit color, underline, hover/focus-visible — Constitution V parity and keyboard focus for free). **Footer placement was the user's explicit call**: a LinkedIn header icon was rejected ("too much"). The constitution's External Links set already named `noon.design` — this is its first on-site appearance. The author links are one leg of the [author-link hand-copy drift surface](#the-author-link-drift-surface) (the footer carries two of the three links; the terminal island's `whoami` egg carries all three).

**Head override — emit a LITERAL attribute value via `set:html` (reusable gotcha).** `src/components/Head.astro` injects a site-wide `<head>` tag (here the Cloudflare Web Analytics beacon — see [build-deploy/deployment](/build-deploy/deployment.md)). The pattern + its WHY: site-wide `<head>` injection that must emit a **literal, un-escaped attribute value** does NOT go through Starlight's `head:` config array — that array renders each entry as `<Tag {...attrs}>` and **Astro HTML-escapes attribute values**, so a JSON attribute like Cloudflare's `data-cf-beacon='{"token": "..."}'` comes out with `&quot;` entities (browsers decode it back at runtime, but it is not the literal tag). Instead, override `Head.astro`: render `<Default />` (still emits Starlight's title/meta/canonical/favicon/fonts and any `head:` config entries), then append the literal tag via `<Fragment set:html={...} />`. Same bare-`<Default />` version note as Footer applies (0.39.2's default Head takes no props/slot — it maps over `Astro.locals.starlightRoute.head`). This `head:`-escaping gotcha is worth recording for any future literal-attribute head injection.

**Head override also carries the SEO/social-share layer (change `kb1r`; per-tool JSON-LD dispatcher, change `pgox`).** After `<Default />`, the same `Head.astro` override appends the **site-wide og:image set** (`og:image` absolute from `Astro.site`, `og:image:width`/`height`/`alt`, `twitter:image`) and a **JSON-LD route dispatcher**: the **homepage-gated** (`Astro.url.pathname === '/'`) WebSite + SoftwareApplication graph (`kb1r`, unchanged by `pgox`) plus a mutually-exclusive **per-tool branch** (`pgox`; root namespace since `3ke3`) that emits a SoftwareApplication + BreadcrumbList `@graph` on every per-tool overview (`/<tool>/`) and readme/commands (`/<tool>/<page>/`) page — both via `JSON.stringify` + `set:html` (reusing the literal-emission pattern above). The homepage additionally overrides `<title>`/`og:title`/`og:type` via `index.mdx` frontmatter `head:` (Starlight's merge dedupes). The full conventions — Starlight's emitted-by-default baseline, the append-vs-override mechanism choice, the 1200×630 OG card + its unwired generator, the redirect-stub exclusion (now the old `/tools/<tool>/*` deep URLs), and the `pgox` dispatcher (the roster-gated pathname split that replaced the `/tools/`-prefix regex at `3ke3`, file-slug name, `root.short` single-sourcing, missing-vs-invalid split, coverage boundary) — live in [seo-social-meta](/conventions/seo-social-meta.md).

## Per-tool GitHub affordance (live Starlight site)

Every tool **overview** page on the live Starlight site (`sites/astro-starlight-terminal1/src/content/docs/tools/<tool>/overview.mdx`) MUST render a top-of-page GitHub affordance: `<GithubButton tool="<slug>" />`, just under the H1. The component (`src/components/GithubButton.astro`, change `vn39`) takes a `tool` slug prop and links to `https://github.com/sahil87/{tool}` — build-time only (no client JS, Constitution I), styled with the terminal `--c-*` tokens (dark-mode parity, Constitution V), with a visible `:focus-visible` ring (Accessibility). It mirrors `CommandReference.astro`'s conventions (`not-content`, scoped `<style>`, frontmatter `interface Props`, missing-slug build guard).

**Build-time star count (change `d9qb`).** The button row now also carries the repo's star count as social proof — `View on GitHub  github.com/sahil87/<tool>  ★ 142  ↗` — rendered **statically at build time** (Constitution I; GitHub's buttons.github.io iframe star buttons were explicitly rejected against Constitution I/VI). The count comes from NEW `src/lib/github-stars.ts`: `getStarCount(tool)` GETs `https://api.github.com/repos/sahil87/<tool>` with native fetch (no new dependency — Constitution VI), sends `Authorization: Bearer` **iff `process.env.GITHUB_TOKEN` is set** (unauthenticated local dev), bounds each request with a 10s `AbortSignal.timeout`, and keeps a **module-level promise cache** (the in-flight Promise is cached, not the value, so concurrent callers during parallel prerendering collapse to exactly one request per repo per build). **Fail-soft by contract**: any failure — network error, non-200 (404 / 403 rate-limit), missing/malformed `stargazers_count` — resolves to `null` with exactly one build-log warning per repo (single `warnOmitted` helper) and never throws; on `null` the button renders **identical to the pre-`d9qb` markup** (no placeholder span). This is the deliberate OPPOSITE of `VersionTable`'s build-stop: that reads committed repo artifacts (`help/*.json`) where absence means a defect reached `main`, while this reads a live third-party API where absence is transient noise. The span sits between the slug and the `↗` arrow: an aria-hidden `★` glyph (accent token) + `formatStarCount` text + an `.sr-only` " GitHub stars" label (the CommandReference sr-only idiom). `formatStarCount` is a separate pure export — `<1000` exact, one decimal below 10k with trailing `.0` dropped (`1234` → `1.2k`, `1000` → `1k`), integer k from 10k up, no millions tier — pinned along with the failure classification and cache-dedup by `scripts/github-stars.test.mjs` (`node --test`, stubbed `globalThis.fetch`). Counts appear on **tool pages only**; the homepage `ls tools/` listing stays clean. The ops side (workflow token, the daily-deploy freshness model the counts ride) lives in [build-deploy/deployment](/build-deploy/deployment.md#build-time-github-api-dependency-star-counts-change-d9qb).

**`.md` → `.mdx` for overviews.** Because importing an Astro component requires MDX, all 7 tool overviews are `.mdx` (not `.md`), mirroring the existing `commands.mdx`. The import path from `src/content/docs/tools/<tool>/` to the component is `../../../../components/GithubButton.astro` (4 `../`). Starlight sidebar slugs are extension-agnostic, so the `.md`→`.mdx` rename itself did not touch `astro.config.mjs`. (The sidebar slug VALUES `tools/<tool>/{overview,readme,commands}` were later rewritten to the root forms `<tool>`/`<tool>/readme`/`<tool>/commands` by change `3ke3`, matching the `slug:` overrides — a separate, deliberate config edit.)

## Design Decisions

- **~~Short pages, not deep docs.~~ Deep, but synced — not hand-copied (revised, change `w32m`, constitution v2.1.0; render placement revised, change `4s3e`, v2.1.1).** The original stance ("the site is a directory; the READMEs are the destination; duplicating them here invites drift") was correct about the *drift* but wrong to conclude *thinness*. The drift it feared came from **hand-copying**, not from depth. The site may now host deep per-tool content because that content is **mechanically synced** from the canonical repo (the [pulled README slice](#pulled-readme-slice-exception-change-w32m)), never hand-copied — so it is fresh by construction and cannot rot. A visitor SHOULD now be able to understand a tool deeply *on the site* without clicking out to GitHub; the tool repo stays canonical (it is where docs are authored), and the daily pull keeps the site in sync. **The overview is thin again (change `4s3e`)** — but unlike the original "link out for depth" thinness, the depth now lives on the site's dedicated `readme` page (sourced from the canonical README), not on GitHub. The thin overview is a directory entry (framing + nav); the depth is one click away *on the site*. *Rejected*: injecting the slice into the overview (the `w32m` model — collides site framing with the canonical slice, double-pitches the tool).
- **Brew install line in every page.** Even though `shll install` installs everything, individual brew lines let visitors install one tool without buying into the whole toolkit.
- **`At a glance`, not `Usage`.** The section is deliberately a teaser, not a tutorial. The name signals "skim this, then read the full README."
- **One dispatch point, not N override slots (change `u4di`).** Starlight gives exactly one `TableOfContents`/`MobileTableOfContents` override slot. Rather than have each generated page type contend for that single slot, a thin `TocDispatcher`/`MobileTocDispatcher` owns it and routes by `Astro.locals.starlightRoute.id` to the per-page ToC (commands → `CommandsToc`, readme → `ReadmeToc`, else `<Default />`). *Why*: a single, traceable routing point; commands behavior is preserved byte-for-byte; the next ToC variant extends the dispatcher with a branch instead of needing a (nonexistent) second slot. *Rejected*: fall-through chaining among the custom components — implicit routing spread across components, harder to trace.
- **Generated/synced pages get a generated rail from their own source (change `u4di`).** A page whose body is a single component call has no headings in the `.mdx` AST, so Starlight's native rail is empty. Each such page builds its own ToC from the page's source of truth (`help/*.json` for commands, `content/<tool>/README.md` for readme) at build time, with a PE scroll-spy enhancing a static list. *Why*: the deepest pages on the site otherwise have the emptiest rail. The readme rail single-sources its slugs through the SAME `createMarkdownProcessor({})` render `ReadmeSlice` uses (`href === id` by construction), so **no `github-slugger` direct dep and no second slug path** — see [readme-extraction](/conventions/readme-extraction.md#slug-single-sourcing-rendered-ids--toc-hrefs-via-one-processor-change-u4di). *Rejected*: a hand-rolled shared `github-slugger` helper (the original intake plan) — a second slug code path that could drift, and a direct dep with no need beyond the already-declared `@astrojs/markdown-remark` (Constitution VI).
- **The thin overview thickened into a job-framed lead + cross-tool links, staying framing-not-depth (change `bees`).** The overview body grew from a single terse sentence to a 3–4-sentence job-framed lead + a `## How it fits` cross-linking subsection, but it is **still thin** — framing and one-line cross-tool context, not the tool's deep docs (those stay on the synced `readme` page). *Why*: content quality caps the markup-SEO payoff of `pgox`/`354p`; a keyword-bearing first paragraph and a connected internal-link graph are the editorial lift, delivered on the site-authored surface the constitution already designates for framing. The H1 (`title:`) was deliberately left as the bare slug to avoid cascading into the sidebar label + the settled `kb1r` title discipline. *Rejected*: changing the frontmatter `title:` to a keyword H1 (cascades to the sidebar / `shll | shll`); a shared "Related tools" component (a future *mechanical* change, out of scope for an editorial pass). Full story in [seo-social-meta → Editorial layer](/conventions/seo-social-meta.md#editorial--content-seo-layer--change-bees).
- **The `vn39` hard rule became load-bearing on the overview framing, and slash-command skills are exempt (change `bees`).** The job-framed leads name validated CLI tokens (`run-kit riff` — `rk riff` pre-`co63`, `shll install`, `git worktree`), so the `vn39` hard rule for hand-written prose now *actively* binds the overview bodies (no longer vacuously satisfied as the framing once was). *Why*: hand-authored site prose must match each tool's `help/<tool>.json` — the `bees` apply ran the cross-check (validate-help 7/7, all tokens resolved). The `/fab-*` slash-command skills are **exempt** — they are Claude Code skills, absent from every help JSON by design, a recognized token category (per the `jf3q` audit + the shipped `idea` overview's "feeds `/fab-new`"); file paths and shell builtins are likewise exempt. *Rejected*: treating `/fab-new` as a `vn39` violation — it contradicts shipped prose and recorded convention.

### Header nav through the SocialIcons slot
**Decision**: `HeaderNav.astro` overrides `components.SocialIcons`, rendering the four text links (Docs · Toolkit · Desktop · GitHub); `social:` is emptied and Discord moves to the footer.
**Why**: Starlight has no nav-links config; overriding the SocialIcons slot is its documented header-links seam and needs no `Header.astro` fork, and it inherits the same mobile hiding (the sidebar carries the same destinations).
**Rejected**: a full `Header.astro` override (forks Starlight layout CSS for four links); sidebar-only navigation (the site structure names a header nav).
*Introduced by*: 260910-it5d-hexokit-site-structure

### `/tools/` retires into `/toolkit/`
**Decision**: the `/tools/` directory page is removed and redirects to `/toolkit/`, whose overview renders the same `ToolsIndex` listing.
**Why**: `/tools/` was the seven-tool table the site structure deliberately removes as a standalone destination; the family listing's home is `/toolkit/`, and a redirect key colliding with a real route fails the Astro build.
**Rejected**: keeping both pages (two directory listings of the same six tools).
*Introduced by*: 260910-it5d-hexokit-site-structure
