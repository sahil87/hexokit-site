# SEO & Social-Share Meta

## Overview

How the live site (`sites/astro-starlight-terminal1`) presents in link previews (Slack, Discord, X, LinkedIn, iMessage) and search snippets. Established by change `kb1r` (2026-06-10), grounded in a live-`<head>` audit of the production site (hexokit.com).

**Division of labor — Starlight baseline + a thin site layer.** Starlight already emits ~80% of SEO hygiene by default on every page: canonical URL, `sitemap-index.xml` (referenced from `robots.txt`), per-page `<title>` + meta description, `og:title`, `og:type`, `og:url`, `og:locale`, `og:description`, `og:site_name`, and `twitter:card=summary_large_image`. The site adds only what Starlight does not: the social-share **image** meta (site-wide, via the `Head.astro` override), homepage-specific `<title>`/`og:title`/`og:type` overrides (frontmatter), and homepage JSON-LD. **Before adding any head tag, check the baseline** — the og:image set could be blindly appended after `<Default />` precisely because Starlight emits no `og:image`/`twitter:image` of its own (no dedupe concern); a tag Starlight *does* emit must instead go through a dedupe-aware mechanism (see the homepage overrides below). Everything here is build-time static markup — no client JS, no dependencies (Constitution I, VI).

## Site-wide og:image set (`Head.astro`)

`src/components/Head.astro` (the registered `components.Head` override — pattern + escaping gotcha documented in [tool-page-rubric → site chrome overrides](/conventions/tool-page-rubric.md#site-chrome-overrides-header-logo-footer-head-change-i2b0)) appends after `<Default />`, on every rendered page:

- `og:image` — **absolute** URL (`https://hexokit.com/og-image.png`). OG scrapers do not resolve relative URLs, so absoluteness is load-bearing. The URL derives from `Astro.site` (`new URL('/og-image.png', Astro.site)`), never hardcoded — `site: 'https://hexokit.com'` in `astro.config.mjs` is the single origin source.
- `og:image:width` 1200 / `og:image:height` 630 / `og:image:alt` (`HexoKit — your tmux, in the browser and on your phone`).
- `twitter:image` — same absolute URL; this is what makes the already-declared `twitter:card=summary_large_image` actually render an image instead of a bare text card (pre-`kb1r`, the asset existed but no meta referenced it).

**Redirect stubs are excluded — deliberately, not a defect.** Astro `redirects:` emit `noindex` meta-refresh stubs that do not render through Starlight's Head component, so they carry no og:image. Scrapers follow them to the canonical tool page, which carries the full set. Verified at `kb1r`: 42/42 rendered pages carry the set; the only og:image-less files were the stubs.

> **The redirect-stub set.** The stubs are the retired deep URLs: per tool, `/tools/<name>` (bare), `/tools/<name>/overview` → `/<mount>/`, `/tools/<name>/readme` → `/<mount>/readme/`, `/tools/<name>/commands` → `/<mount>/commands/` — keyed by every name the `/tools/` namespace ever used (the slug AND its `legacyMounts`), plus one stub per committed docs/site page and, for HexoKit, the legacy-mount set `/run-kit{,/readme,/commands,/<docs-site page>}` → `/docs/…` (enumerated by `docsSiteRedirectEntries` + the roster's `legacyMounts`, see [docs-site-tree → redirect enumeration](/conventions/docs-site-tree.md#the-redirect-enumeration)); plus the retired family pages (`/tools` → `/toolkit/`, `/getting-started/*` and `/workflows/*` → `/toolkit/…`). Same invariant holds: the stubs are `noindex` shells with no og:image, and scrapers follow them to the canonical `/<mount>/…` page which carries the full set.

## The OG card asset (`public/og-image.png` + `scripts/generate-og-image.mjs`)

The shared image is a **committed static asset**, exactly **1200×630** (the ~1.91:1 shape link-preview scrapers want — the prior 512×512 square rendered wrong). Composition: a dark terminal-window card in the site's own aesthetic — `terminal.css` dark palette, titlebar dots, a `$` prompt line, the `hexokit` wordmark, the tagline `Your tmux, in the browser and on your phone.`, a `hexokit.com` footer line — set in JetBrains Mono from the already-declared `@fontsource/jetbrains-mono` dependency, legible at ~quarter scale (Slack/X preview sizes). The card is a fixed dark design regardless of site theme, so Constitution V (dark-mode parity) is not implicated by the asset. (The favicon is unchanged by the identity work — `public/favicon.svg` is byte-identical to run-kit's `assets/logo.svg`, which already is the HexoKit mark; see [tool-page-rubric → site chrome overrides](/conventions/tool-page-rubric.md#site-chrome-overrides-header-logo-footer-head-change-i2b0).)

**Generation is OUT of the build (Constitution VI).** `sites/astro-starlight-terminal1/scripts/generate-og-image.mjs` is a **one-off, unwired** generator: node stdlib only, it writes a self-contained HTML mock and screenshots it at 1200×630 with the Playwright-cached `chrome-headless-shell` binary already on the machine. It is NOT referenced from `package.json`, adds zero runtime or build dependencies, and exists purely for reproducibility — re-run it manually to regenerate the card, then verify with `file public/og-image.png` (must report `1200 x 630`). *Rejected*: SVG→PNG converters (none installed); adding `sharp`/`playwright` as devDependencies (Constitution VI).

## Homepage `<head>` overrides (`index.mdx` frontmatter)

`src/content/docs/index.mdx` carries frontmatter `head:` entries that override Starlight's defaults **on the homepage only**:

- `title` tag → **`HexoKit — your tmux, in the browser and on your phone`** (no site-title suffix) — carries the product keyword framing.
- `og:title` meta → same string.
- `og:type` meta → `website` (correct for a landing page; every other page keeps Starlight's default `article`, correct for docs content).

**Mechanism**: Starlight's head-merging gives frontmatter `head:` entries priority over its defaults and **dedupes** the singleton `<title>` and same-`property` metas — so the built homepage carries exactly one of each. This is the dedupe-aware path for overriding tags Starlight already emits (contrast the og:image set above, which is append-only because Starlight emits none). The visible hero H1 is unaffected — the splash hero renders from the `hero:` block, not the page title.

**Scope note:** all non-homepage titles keep the `{page} | HexoKit` suffix (the site title is `HexoKit` in `astro.config.mjs`). The `shll | HexoKit` title on the shll *tool's* overview page (`/shll/` — a page legitimately named after the tool) is Starlight's correct default.

## JSON-LD: a route dispatcher in `Head.astro` (NOT frontmatter)

JSON-LD is authored as a **route dispatcher** in `src/components/Head.astro` — two mutually-exclusive branches, each emitting its own `<script type="application/ld+json">` block. JSON-LD is **inert data, not executable JS** — no Constitution I conflict.

**Placement decision (`kb1r`)**: all JSON-LD is emitted from `Head.astro` (gated on the route), serializing a plain JS object via `JSON.stringify` into `set:html`. This keeps the JSON authorable as a real object, and is safe by construction — `JSON.stringify` of these objects never produces `<` or raw HTML, so the body survives emission byte-exact (verified at `kb1r`: `JSON.parse` succeeds on the script body extracted from built HTML). *Rejected*: an `index.mdx` frontmatter `head:` entry with the JSON as a string `content:` — a large JSON blob inside YAML frontmatter is fragile and unreadable, and is exactly the MDX/YAML escaping friction the intake flagged as a drop trigger; it also can't reach per-route help-JSON data.

### Homepage branch — WebSite + SoftwareApplication

One block on the homepage only (gated on `Astro.url.pathname === '/'`), carrying a `@graph` of two entities: `WebSite` (name `HexoKit`, url from `Astro.site` origin) and `SoftwareApplication` (name `HexoKit`, description `Your tmux, in the browser and on your phone.`, `applicationCategory: DeveloperApplication`, `operatingSystem: macOS, Linux`, a free `Offer`, url `https://github.com/sahil87/run-kit` via the roster's `repoFor('hexokit')`).

### Per-tool branch — SoftwareApplication + BreadcrumbList (mount-gated)

Every **per-tool page** emits its own inert `application/ld+json` `@graph` of two nodes — a per-tool `SoftwareApplication` and a `BreadcrumbList` — mirroring the homepage `@graph` shape (one `<script>`, two entities, `JSON.stringify` + `set:html`). The two branches are mutually exclusive: a tool page can never be `/`, and `/` never matches the tool-page shapes.

> **The per-tool pages live at the site ROOT, keyed by the roster `mount`.** The covered pages are the overview (`/<mount>/`, 1 segment — `/docs/` for HexoKit) and readme/commands (`/<mount>/<page>/`, 2 segments). Parity across tools: exactly the overview/readme/commands pages are covered — nested docs-site pages stay uncovered.

- **Route detection — `Astro.url.pathname` split into segments, mount-gated (not `starlightRoute.id`).** The branch parses `Astro.url.pathname` (stripped of leading/trailing slashes, split on `/`) and matches **two shapes**, both gated on the shared roster's mount set (`isToolMount` from `src/lib/tool-slugs.ts` — the typed re-export of [tool-roster.mjs](/conventions/tool-roster.md)) — a bare `/<x>/` shape would otherwise match ANY root page (`toolkit`, `reference`, `desktop`, …). The captured segment is the **mount**; the slug is resolved via `slugForMount`:
  - **overview** — 1 segment `/<mount>/`, `<mount>` ∈ mounts → no page crumb.
  - **readme/commands** — 2 segments `/<mount>/<page>/`, `<mount>` ∈ mounts AND `<page>` ∈ `{readme, commands}` (a small `PAGE_LABELS` map) → page crumb present.
  This keeps the **same pathname-gate idiom** as the homepage branch (`pathname === '/'`) in this same file — one consistent gate idiom, not a mix with the `TocDispatcher`'s `starlightRoute.id` regexes.
- **`SoftwareApplication` node**: `name` = the roster **label** via `labelFor(slug)` (`HexoKit` for the `/docs/` pages, the slug-cased label for companions) — the entity names the software product, matching the route + breadcrumb label + GitHub url. `description` = `root.short` read from `help/<slug>.json` (single-sourced; see below). `applicationCategory: DeveloperApplication`, `operatingSystem: 'macOS, Linux'`, a free `Offer`, `url: https://github.com/sahil87/<repoFor(slug)>` — the same shape as the homepage `SoftwareApplication` node for graph consistency (all seven are free macOS+Linux CLIs; HexoKit's url resolves to `sahil87/run-kit`).
- **`BreadcrumbList` node** (crumb depth splits by tool kind and page shape): **all `item` URLs absolute, derived from `Astro.site`** (`new URL(path, Astro.site).href`) — never hardcoded, the same absolute-URL discipline `kb1r` established for og:image (`site: 'https://hexokit.com'` is the single origin source). The crumb items:
  - Position 1 `Home` → `/`.
  - Position 2 `Docs` → **`/docs/`** for the product (`hexokit`), or `Toolkit` → **`/toolkit/`** for the companions.
  - Position 3 (companions only) `<label>` → **`/<mount>/`** — the tool's canonical root URL (its overview). The product has no position-3 tool crumb — `/docs/` IS its position-2 destination.
  - Final `<page>` → **`/<mount>/<page>/`** — present **only** for the readme/commands (2-segment) pages; the overview page emits no page crumb (the overview IS the tool crumb's destination). The page label comes from the small site-authored `PAGE_LABELS` map (`readme→Readme`, `commands→Commands`).

**Single-sourcing — the `description` comes from `help/<slug>.json` `root.short`, never hand-copied.** The binding anti-drift rule (constitution Tool-Page Depth, `vn39`, [help-collection](/conventions/help-collection.md)) applies here too: the SoftwareApplication `description` is read at build time via `repoRootFromModuleUrl(import.meta.url)` + `HelpDocSchema.parse` (the same shared libs `CommandReference`/`VersionTable`/`CommandIndex`/`ToolsIndex` use), never retyped. The llms.txt sibling drives its tool one-liners from the same field, so `root.short` is the one canonical one-liner.

> **Verbatim `root.short` includes the binary prefix — an intentional divergence.** The product's `root.short` (`help/hexokit.json`, envelope `tool: "run-kit"`) is binary-prefixed — `"run-kit — tmux session manager with web UI"` — and rendered **verbatim** in both the SoftwareApplication `description` and the `/toolkit/` listing, so it differs from the homepage `TerminalPrompt`, which strips the prefix via `stripToolPrefix`. This is deliberate: a single verbatim source beats adding a second, divergent strip path — single-sourcing wins over cosmetic consistency. Not a bug.

**Missing-vs-invalid failure split — mirrors `CommandReference.astro`, NOT `VersionTable`'s build-stop.** Because the per-tool JSON-LD is **inert SEO metadata** (not a correctness-critical committed artifact like the `/toolkit/` directory listing), the failure posture is the soft split:

- **Missing file (ENOENT)** → emit the `SoftwareApplication` node **without its `description` field** (keeping `name`/`url`/`applicationCategory`/`operatingSystem`/`offers` — all site-authored / derivable without the help JSON) and **continue the build**; the `BreadcrumbList` needs no help JSON and **always emits**. An absent help file is an expected interim state for a not-yet-landed producer; a missing description must not stop the build (resolved at clarify #10: omit description only, NOT the whole node). A non-ENOENT read error (e.g. EACCES) is a real fault and rethrows.
- **Present but schema-invalid** → `HelpDocSchema.parse` throws, wrapped with the filename, so `astro build` FAILS — a committed malformed help file is a defect that must not deploy (the `CommandReference` invalid-file contract).

> **Coverage boundary — overview/readme/commands pages only (known/accepted).** The gate matches only the **overview** (`/<mount>/`, 1 segment) and **readme/commands** (`/<mount>/<page>/`, 2 segments, `page ∈ {readme, commands}`) pages — exactly the reserved per-tool page set. The dynamic route `src/pages/[mount]/[...path].astro` renders **nested docs-site pages** at `/<mount>/<path>` (e.g. `/idea/install`, `/docs/skill/mux` — see [docs-site-tree](/conventions/docs-site-tree.md)); those pages emit **no** JSON-LD (no error, just absent). A single-segment docs-site page does NOT collide with the overview gate because the gate additionally requires the segment to be a roster **mount** while a page path is not one, and a 2-segment page like `/idea/install` falls through because `install ∉ {readme, commands}`. Recorded as a known, accepted boundary, NOT a defect. If nested docs-site JSON-LD is ever wanted, this gate is where to extend it.

## Agent-discoverability layer (`/llms.txt` + `/llms-full.txt`) — change `354p`

The **agent-facing sibling** of the SEO layer above. Where og:image/JSON-LD make the site legible to crawlers and social scrapers, the two `llmstxt.org`-convention endpoints make it legible to **coding agents**: a single-fetch index plus a full-content dump, discovered by convention at `/llms.txt` and `/llms-full.txt`. Both are **build-time Astro static endpoints** (`src/pages/llms.txt.ts`, `src/pages/llms-full.txt.ts`) returning `new Response(body, { headers: { 'Content-Type': 'text/plain; charset=utf-8' } })` — no SSR, no runtime fetch (Constitution I), zero new deps (Constitution VI). Both emit into `dist/llms.txt` / `dist/llms-full.txt`. The shared cross-boundary reads live in `src/lib/llms.ts` (`TOOLS`, `stripToolPrefix`, `toolShort`, `readHelpDoc`, `readReadmeSlice`, `renderCommandTree`, `flattenMdx`); the pure helpers are pinned by `scripts/llms.test.mjs` (`node --test`, type-stripping — same toolchain as `validate-help.mjs`/`parse-help.test.mjs`).

### `/llms.txt` — the curated index

H1 `# HexoKit — your tmux, in the browser and on your phone` + a one-line blockquote summary (the product framing + the six companion CLIs) + three bulleted link sections:

- **`## Docs`** — the product's pages: `/docs/` overview, `/docs/readme/`, `/docs/commands/`, then **one bullet per committed HexoKit docs/site page** via `collectDocsSitePages` (mechanical — label = the page title, path `/docs/<path>/`; no hand-maintained list).
- **`## Toolkit`** — the `/toolkit/` pages + `/desktop/`, then one bullet per companion `/<mount>/` with the `root.short` one-liner (fallback: the overview `description`, keyed by `slugForMount(entry.id)` since the overview entry id is the mount).
- **`## Reference`** — the command index.

- **Single-source the tool one-liners — derive, never retype (the anti-drift rule).** Each tool description is read from `help/<slug>.json` `root.short` (the canonical machine source) via `toolShort()`, which uses the `repoRootFromModuleUrl` (`help/`-anchored ascent) + `HelpDocSchema` pattern — **NOT** `parse-help.ts` (which parses raw `-h` *text*; `root.short` lives on the structured `HelpDoc` envelope). The leading `<bin> — ` prefix is **stripped** when present (`stripToolPrefix`, mirroring `terminal-toolcard.ts` — the product's `root.short` is binary-prefixed `"run-kit — …"`; the strip is binary-name-agnostic, and the bullet's link text already carries the tool name). This is the same `vn39` / [Tool-Page-Depth](/conventions/tool-page-rubric.md) anti-drift rule that governs the rest of the site: the codebase already holds documented hand-copies of tool descriptions; the endpoints MUST NOT add another one. **Fallback chain:** missing/empty `root.short` → the tool's overview frontmatter `description` (read via `getCollection('docs')`, the same content the HTML pages render) → a noted-omission bullet (never an empty/`undefined` bullet, never a build-stop).

### `/llms-full.txt` — the full-content dump

Opens with `# HexoKit — full content`, then **iterates `TOOL_ROSTER` in display order** (product first; each section headed by `labelFor(slug)` — `## HexoKit`, `## fab-kit`, …), concatenating per tool: (a) the committed README slice at `<repo-root>/content/<slug>/README.md` — read **verbatim** (`readReadmeSlice`; already the deduced slice — do NOT re-run `extractReadme`), and (b) a `### Commands` plain-text command tree from the validated `HelpDoc` (`renderCommandTree`). It THEN appends the **hand-authored MDX** sourced via `getCollection('docs')`, grouped as **`Toolkit`** (entry ids `toolkit`, `toolkit/*`, `desktop`), **`Reference`**, and **`Tool overviews`** (entries whose id is a tool mount).

- **The content boundary — synced content PLUS site-authored MDX (intake Assumption #5, resolved the non-default way).** The backlog *recommended* mechanically-synced content only; the user resolved it to **include the hand-authored MDX too**. So `llms-full.txt` is no longer "synced-only" — an edit to a site-authored MDX page is now **also an `llms-full.txt` content change**. This coupling is **intentional, not accidental**: the synced parts (README slices + help) ride the existing daily `refresh-readme.yml` / help-refresh cascade (no new schedule), and the MDX parts change only on a human edit — the same refresh cadence as the HTML pages they mirror.
- **Flatten is applied ONLY to the MDX; README slices are emitted verbatim (load-bearing).** MDX is not plain markdown — `flattenMdx` does a *pragmatic* strip of leading frontmatter, `import` lines, and **Capitalised** JSX component tags (keeping their text children), leaving readable prose for the `text/plain` dump (exact fidelity is explicitly not required — Constitution VI; a full MDX compiler was rejected). `flattenMdx` is **NOT** applied to the README slices: they pass through `readReadmeSlice` untouched, so the `<TAB>` / `<N>` placeholder tokens the pulled READMEs carry (e.g. `content/hop/README.md`) **survive verbatim** into the dump rather than being mistaken for JSX and stripped. The boundary is: synced slice = verbatim; site MDX = flattened.

### Shared discipline with the SEO layer

- **Absolute URLs from `Astro.site`, never hardcoded** — every emitted link is site-absolute, via **two** mechanisms both keyed on the endpoint context `site` (`https://hexokit.com`, the single origin source in `astro.config.mjs`): the *curated* links in `llms.txt` (docs / toolkit / reference) are **built** via `new URL(pathname, site)`; the *appended docs content* in `llms-full.txt` (README slices + flattened MDX) carries its own root-relative links (e.g. `[overview](/idea/)`, the homepage's `<a href="/idea/">` — the root `/<mount>/` links), so it is **rewritten** to absolute by `absolutize(content, origin)` — a targeted pass over markdown `](/path)` and HTML `href`/`src="/path"` forms only (already-absolute / protocol-relative / fragment / doc-relative targets, and the leading-`/`-less `<N>`-style tokens in README prose, are left untouched). This is the *same* absoluteness discipline the og:image set above relies on (OG scrapers and agents alike do not resolve relative URLs).
- **Per-tool fail-soft (skip-degrade, not build-stop)** — a tool whose README slice or help JSON is missing degrades to a noted omission and the build CONTINUES, mirroring the [help-collection per-tool skip-degrade](/conventions/help-collection.md#rendering-consumer-3-the-homepage-terminals-tool-cards-change-37ng), explicitly NOT `VersionTable`'s unconditional build-stop. (The `HelpDocSchema` read still re-throws a genuine parse/validation error — a *present-but-invalid* committed file is a defect that must not be masked — same discipline as `CommandReference`.)

### `robots.txt` left unchanged (explicit non-change)

`public/robots.txt` is **byte-unchanged**. The files are discovered by *convention* at `/llms.txt` / `/llms-full.txt`; there is no agreed `Sitemap:`-style line for them, and adding a non-standard reference risks confusing real crawlers. Starlight's existing `robots.txt` reference to `sitemap-index.xml` stays untouched.

### Honest caveat (carry it — do not oversell)

`llms.txt` is a **PROPOSED convention, not a guaranteed-consumed standard** like `robots.txt` / sitemaps. This layer is **cheap insurance and a structure-forcing function**, not a guaranteed traffic source. Recorded so a future reader does not mistake the endpoints for a load-bearing distribution channel.

### Accepted drift surface (low-severity, fails loudly)

`src/lib/llms.ts`'s `TOOLS` is **derived** from the shared roster (`TOOL_SLUGS` from [tool-roster.mjs](/conventions/tool-roster.md), display order) — there is no hand-maintained slug list left in the endpoints. (The homepage terminal instead enumerates `help/` via `readdirSync` — see [help-collection](/conventions/help-collection.md).) What remains hand-authored in the endpoints: the curated section labels/descriptions and the `toolkit`/`desktop` group matchers — a stale matcher surfaces as a missing bullet in the output, visible on inspection.

## Editorial / content SEO layer — change `bees`

The third of the SEO batch (after `354p`/llms.txt and `pgox`/JSON-LD, which were *mechanical*). `bees` is the **editorial** pass — content quality, not markup. It edited only **site-authored content** under `sites/astro-starlight-terminal1/src/content/docs/` (the 7 `tools/<tool>/overview.mdx`, `getting-started/overview.md`, and the homepage `index.mdx` `cat ABOUT.md` prose) — **never** the synced `readme.mdx` slice, the generated `commands.mdx`, or any `help/<tool>.json` (Constitution § Tool-Page Depth; see [tool-page-rubric](/conventions/tool-page-rubric.md)). Zero new deps, content-only MDX/Markdown edits (Constitution I, VI).

### Meta descriptions are HAND-AUTHORED + SEO-optimized — the INVERSE of `pgox`/`354p`

This is the load-bearing contrast to record. The `pgox` JSON-LD `SoftwareApplication.description` node and the `354p` llms.txt tool one-liners are **single-sourced from `help/<tool>.json` `root.short`** (verbatim, anti-drift). The frontmatter `description` metas — the search-snippet / og:description surface — go the **opposite way**: each is a **unique, hand-authored, keyword-optimized** sentence, deliberately **NOT** downgraded to `root.short`.

- **Why the inverse decision.** A live audit at `bees` found every editable page already carried a hand-authored `description` markedly more keyword-rich than the terser `root.short` (e.g. fab-kit's `6-stage pipeline that forces AI agents to plan before they code.` vs. `root.short`'s `Fab workflow engine — single binary replacement for kit shell scripts`). The backlog *recommended* single-sourcing the metas from `help/<tool>.json`; the user resolved it the other way — **keep & editorially refine the hand-authored descriptions** (≤~155 chars, lead with the highest-value keyword, name the *job* not the binary, unique across the site). `root.short` stays the source ONLY for the `pgox` JSON-LD node and the `354p` llms.txt bullets, where it already lives.
- **So `root.short` and the meta description are two DIFFERENT strings by design.** Do not "reconcile" them — the JSON-LD/llms.txt description is the machine-canonical one-liner (single-sourced); the meta `description` is the human-optimized snippet (hand-authored). Both are correct; they serve different consumers.
- **The meta descriptions are therefore a hand-authored-prose surface — the `vn39` HARD rule binds them** (any command/flag named must exist in `help/<tool>.json`), not the report-only mode that governs the synced README slice. At `bees` the descriptions named no commands, but the rule applies if a future refinement adds one.

### Cross-tool internal linking — the `idea→fab-kit→wt→run-kit` graph (the highest-value `bees` item)

Before `bees`, the 7 tool overviews carried **zero** cross-tool links — the toolkit read as 7 disconnected islands (weak internal-link equity, weak "these tools compose" signal for crawlers and agents). `bees` wired the toolkit into a connected graph via a **`## How it fits` subsection** added to every `tools/<tool>/overview.mdx` body — a one-line-context paragraph linking the adjacent tools in the workflow chain.

- **The chain**: `idea → fab-kit → wt → run-kit` (backlog → plan → isolated worktree → dashboard), with **`tu`** (cost) and **`hop`** (repo nav) as cross-cutting, and **`shll`** as the bootstrap. Realized per-page link map: idea→{fab-kit, wt, tu}; fab-kit→{idea, wt, run-kit}; wt→{fab-kit, run-kit}; run-kit→{wt, tu}; tu→{fab-kit, run-kit}; hop→{idea, wt}; shll→{idea, fab-kit, wt, run-kit} + the install page.
- **Link form — site-absolute `/<mount>/`.** Cross-tool links → `/<mount>/`, sibling links → `/<mount>/readme/` and `/<mount>/commands/` (HexoKit's overview is `/docs/`). Under the flat root mount the relative form would resolve wrong (`../readme/` from `/idea/` → `/readme/`), so site-absolute is the simplest correct form. Targets are the canonical `/<mount>/` entry pages — the constitutional [directory-entry role of the overview](/conventions/tool-page-rubric.md#pulled-readme-slice-exception-change-w32m). The `shll` overview's bootstrap link to the install page is `/toolkit/install/` (it points out of the tool namespace).
- **The `/toolkit/` overview's ASCII workflow diagram is navigable too.** Its `idea → fab-kit → wt → HexoKit` chain tool names (and the surrounding `tu`/`hop`/`shll` prose) are **site-absolute `/<mount>/` links** (root-relative from a page outside the tool namespace). The diagram is a clickable map, not just an illustration (this also satisfies the Constitution Accessibility SHOULD for decorative diagrams, the same way [`ld0j`](/conventions/tool-page-rubric.md#homepage-newcomer-content-blocks-hand-authored-change-ld0j) moved the homepage diagram links inline).

### Job-framed lead sentences on the overviews (the H1-substitute framing)

The bare-slug Starlight `title:` (the H1) was **not changed** — it cascades to the sidebar label and the settled [`kb1r` title discipline](#homepage-head-overrides-indexmdx-frontmatter). Instead, each overview body's opening was expanded from a terse 1–2-sentence framing to a **3–4-sentence job-framed lead** ("what is `<tool>` / why use it / who it's for") that surfaces ranking keywords in the first indexable paragraph. The homepage `cat ABOUT.md` prose and the toolkit overview intro were keyword-sharpened by **refining existing copy only** — no new claims, no new sections; the homepage `head:` overrides block, hero `tagline`, and install/`whoami` blocks were left byte-for-byte (the `ld0j` sourced-copy discipline preserved). This thickening of the overview body is the rubric change recorded in [tool-page-rubric](/conventions/tool-page-rubric.md).

## Design Decisions

- **A thin layer over Starlight's baseline, not a meta framework.** The audit showed Starlight covers most SEO hygiene already; the fix is a few appended tags in the existing Head override + two frontmatter overrides + one regenerated asset. *Rejected*: any SEO integration/plugin — no page-visible need beyond these tags (Constitution VI).
- **Append vs. override, chosen per tag.** Tags Starlight does not emit (the og:image set) are appended after `<Default />` in the Head override; tags it does emit (`title`, `og:title`, `og:type`) are overridden through frontmatter `head:` where Starlight's merge dedupes. Using the right mechanism per tag is what keeps every built page at exactly one instance of each.
- **JSON-LD lives beside the other literal-emission head injections.** `Head.astro` already owned the `set:html` literal-emission pattern (the Cloudflare beacon, change `i2b0`); the JSON-LD reuses it rather than introducing a second authoring home in frontmatter.
- **One JSON-LD authoring home, extended into a route dispatcher (change `pgox`).** Rather than add a second authoring home for per-tool structured data, `pgox` extended the existing route-gated `Head.astro` block into a dispatcher: the homepage branch and a mutually-exclusive tool-page branch. *Why*: `Head.astro` already owns all JSON-LD via the `set:html` pattern and is the only place that can reach per-route `help/<slug>.json` data at build time; a frontmatter `head:` blob can't (it's per-page string YAML, fragile, and data-blind). The two branches gate on the same `Astro.url.pathname` idiom (homepage `=== '/'`; tool pages a pathname split gated on the roster's mount set) for consistency within the file. *Rejected*: `starlightRoute.id` + the `TocDispatcher` regexes (valid, but mixes idioms in this file).
- **Per-tool failure posture follows `CommandReference`, not `VersionTable` (change `pgox`).** Inert SEO metadata uses the soft missing-vs-invalid split (ENOENT → omit description + continue; invalid → build-fail) because a missing producer help file is a transient/interim state, not a deploy-blocking defect. This deliberately differs from the directory listing (`/toolkit/`, rendering `ToolsIndex`), which uses `VersionTable`'s build-stop posture because an incomplete committed directory listing IS a defect. Two surfaces, two correctness criticalities — see [tool-page-rubric](/conventions/tool-page-rubric.md#tools-index-page--the-tools-directory-landing-change-pgox).
- **Mount gate via the shared roster.** The per-tool JSON-LD gate splits `Astro.url.pathname` into segments and checks the first against the roster's mount set (`isToolMount` from `src/lib/tool-slugs.ts` — the typed re-export of [tool-roster.mjs](/conventions/tool-roster.md)), matching the 1-segment overview and 2-segment readme/commands shapes; the slug is resolved via `slugForMount`. *Why*: one shared source of truth for the tool mount set (same roster as `commands-toc.ts`/`readme-toc.ts`/llms), and the only correct way to tell `/idea/` (a tool) from `/toolkit/` (not) — a bare `([^/]+)` regex with no membership check false-positives against root routes.
- **The `pageLabel()` title-case fallback was removed (change `3ke3`).** `pgox` carried a title-cased fallback (`slug.charAt(0).toUpperCase() + slug.slice(1)`) for an unmatched BreadcrumbList page-label slug — a minor divergence from `docs-site-sidebar.mjs`'s `titleizeTail`. `3ke3` **deleted it**: the 2-segment shape now matches only `page ∈ {readme, commands}` (both in the explicit `PAGE_LABELS` map) and the overview is the 1-segment shape (no page crumb), so no unmatched-slug case can reach a label lookup — the fallback became dead code. If nested docs-site JSON-LD is ever added (the coverage boundary above), reintroduce a label strategy for those slugs there.
- **The OG card is an artifact, its generator is a tool — only the artifact ships.** Committing the PNG keeps the build dependency-free; committing the unwired script keeps the card reproducible. Neither couples to `package.json`.
- **The agent layer is a sibling of the SEO layer, co-located here, not a new file (change `354p`).** `/llms.txt` is to coding agents what og:image/JSON-LD are to scrapers — the SAME disciplines (absolute URLs from `Astro.site`, single-source-not-hand-copy, build-time static, zero deps), a different audience. The memory was placed as a delimited section *in this file* rather than a new sibling so the crawler + agent discoverability story stays co-located (intake Assumption #6). *Rejected*: a separate `agent-discoverability.md` — would scatter one coherent "how the site presents to non-human consumers" story across two files.
- **`llms-full.txt` is coupled to site-authored MDX by design (change `354p`).** Resolving the intake's one open call the non-default way (include hand-authored MDX, not synced-only) means an MDX edit is now also an `llms-full.txt` content change. Accepted because it keeps the dump single-sourced from the same `getCollection('docs')` content the HTML pages render — no new hand-copy — and the staleness still rides the existing daily refresh. *Rejected*: synced-content-only (the backlog's recommendation) — would have omitted getting-started/workflows/philosophy prose an agent ingesting the toolkit wants. *Rejected*: a full MDX compiler pass — `flattenMdx`'s pragmatic tag/import strip is sufficient for a `text/plain` dump (Constitution VI).
- **Flatten the MDX, emit the README slices verbatim (change `354p`).** `flattenMdx` runs ONLY on the `getCollection('docs')` bodies; `readReadmeSlice` returns the committed slice untouched. This is deliberate — the pulled READMEs carry `<TAB>`/`<N>` placeholder tokens that a JSX-tag strip would corrupt, and the slice is already the canonical deduced prose. *Rejected*: a uniform flatten over both sources — would mangle the README placeholders for no benefit.
- **Meta descriptions stay hand-authored, NOT single-sourced from `root.short` (change `bees`).** The deliberate inverse of `pgox`/`354p` (which DO single-source `root.short`). *Why*: the existing hand-authored frontmatter `description`s are unique and markedly more keyword-rich than the terser `root.short`; downgrading them to the machine one-liner would *regress* the search-snippet surface. So `root.short` is the canonical machine description (JSON-LD + llms.txt), and the meta `description` is the human-optimized snippet — two strings, two consumers, both correct. *Rejected*: the backlog's recommendation to single-source the metas from `help/<tool>.json` — it would have downgraded a better surface to a worse one. (User-resolved at intake, the central SRAD question.)
- **Cross-tool linking via a `## How it fits` subsection on every overview, not a shared component (change `bees`).** The connected `idea→fab-kit→wt→run-kit` graph is realized as hand-authored MDX prose+links in each overview body, reusing the existing relative-link idiom — zero new components, zero new deps (Constitution VI). *Why*: the overview is the site-authored directory entry; one-line cross-tool context is exactly its job (Constitution § Tool-Page Depth). *Rejected*: a shared "Related tools" component — deferred as a *future mechanical* change, out of scope for an editorial pass.
